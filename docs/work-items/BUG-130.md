# BUG-130：复杂球鼻艏 `export(stl)` 在剖分后 worker 崩溃（0xC0000005）

## 当前摘要：离线复核与修复提案（2026-11-16）

分类：**已确认失败触发模型，根因待定位，未修复**。类型：缺陷 / 原生worker崩溃。优先级：P1。目标版本：未排期。已有两次原生失败记录，本轮不再连接或重复触发；未修改源代码、未构建执行器、未清保护。

结合原始作业、本机 SDK、官方文档和 `native/generic.cpp:4211–4242` 离线核对后，修正初次登记的过强结论：

1. **本体约14m长，不是78m。** 包络X=64094.616～78095.159mm，跨度约14000.543mm；对角线约14602.7mm。X坐标不能当作物体长度。
2. **不能归因“只在尺度”。** 旧同尺度球鼻艏 `bulb_verified_03989988` 的 STL 作业 `37a35d07991647ada1db2170cc61316d` 已成功，文件48847489字节、197118个三角片。旧件和新件的曲面复杂度/修剪拓扑、会话和时间不同；小件对照不构成只改变尺度的单变量试验。
3. **SDK第四参语义已核实。** `PRO_B_FALSE` 是不包含quilt/facets的选择，不是相对/绝对弦高；0.1是0～1的角控制参数，不能当作0.1度。`ProPart.h:105–155` 和官方 `ProPartTessellate` 页面一致。
4. **目前只证明worker访问冲突。** 两次日志的 `PHASE=export` 尾部相同，整份日志的时间不同，并非整份字节相同；`ProArraySizeGet=0` 是返回成功，不是n=0。缺少实际n、每面计数、面片索引、内存峰值和故障栈，不能把崩溃精确归到某条数组语句或释放函数，更不能据此认定Creo主进程退出。
5. **两次STL都是0字节。** 已创建文件但没有正常交付。源码先close文件再调用 `ProPartTessellationFree`，因此“释放时崩溃”不是目前最有力的定位；仍需阶段日志和堆栈确认。
6. **STEP成功不是剖分正确性证明。** 只说明该STEP导出成功；不排除局部退化、修剪边界、异常返回数组、SDK/IPC或应用侧内存问题。远程桌面目前缺少支持其致因的证据，但没有独立进程/系统记录和受控环境对照，不写成已严格排除。

已见代码风险是：未经判空/边界检查便访问 `s.facets[j]`、`s.vertices[indices[k]]`；没有非有限坐标/计数溢出防护；部分C++异常路径不释放Toolkit结果；写盘/close失败没有核验。它们需要修复，但没有堆栈不能称作此次已证根因。当前 `ofstream` 已逐片写文件，没有另攒一份应用网格；仅增加“流式写盘”不会改变 `ProPartTessellate` 整件分配的峰值。

**推荐方案**：先补可定位到面/片/IO/释放的诊断，优先验证官方文件式 `ProIntfSliceFileWithOptionsMdlnameExport` / `PRO_SLA_ASCII_FILE`（参数为3元素ProArray，明确弦高/角控制），绕开worker对整件嵌套剖分指针的解引用；同质量不能通过时再验证逐实体面剖分。可调质量参数在稳定路径后接入，不使用未验证的BBox自动公式，也不自动降精度重试。此前建议的 `max(0.01,diag*1e-6)` 对本件约为0.0146mm，会比现有0.05mm更细。

**完整任务、文件、接口、测试矩阵与完成标准**：[BUG-130 修复计划](../superpowers/plans/2026-11-16-bug130-stl-export.md)。文件式导出和逐面备选都只是离线核对可用的API，尚无本故障模型的实机结果。只读unknown保护及显式探测语义保持；历史restore_baseline记录不是后续自动恢复的授权。

本轮审阅工作区：`main` / `4de47e75af4f685ed71b5645e96826d9020d520b`，dirty=true，保留球鼻艏等既有未提交产物。原模型创建/旧STL成功的worker身份记录为 `30a18e88…`、source_digest `fd85fe35…`，与初次故障记录一致，但故障作业本身未提供逐任务自报指纹，不将“记录一致”升级为完整的同构建/同会话受控试验。

## 原登记摘要（2026-11-16，初步假设；以上复核为准）

分类：**已定位到触发条件，未修复**。类型：缺陷 / 原生崩溃。优先级：P1。目标版本：未排期。

结论：`creo_export_model(format="stl")` 在 `bulb_bulged`（78 m 长、半体 49.5 m² 双曲率放样面）上连续两次以原生 `0xC0000005` 退出；同一通道在 6270 mm³ 的小零件上成功，同一模型导出 STEP 也成功。**因此不是导出通道坏了，也不是远程桌面导致，差异只在零件尺度**。崩溃点在 `ProPartTessellate(…, 0.05, 0.1, …)` 与 `ProArraySizeGet` 都成功返回之后。

环境：MCP_CREO_MechDog 0.26.0，Creo 12.4.0.0（`release_numeric=44`），worker SHA256 `30a18e88b8977765f5b2438370b08339bac3f58136d3ebac1974bd3dcca3f41b`，source_digest `fd85fe3530cc02cfe40672c8239c7c3e467554ffc05c93b26c0caa671024f211`，session fingerprint `11535666132601238752`。

## 现象与复现

被测模型 `bulb_bulged`，model_id `cda665ef57d54847bb6970e5787e7fbd`，revision 8，体积 `55 052 144 699.379 mm³`，包围盒 `[[64094.616, -1818.187, -6600.120], [78095.159, 1818.187, -4599.871]]`，3 个曲面、43 个特征、2 个体。第二次崩溃时 Toolkit 显式探测已通过（`toolkit_code=0`、`mode=explicit_live`、`busy=false`）。

最小复现：对上述模型调用

```
creo_export_model(model_id="cda665ef57d54847bb6970e5787e7fbd", format="stl")
```

两次结果一致：

| 作业 | 开始 | 结束 | 耗时 | 状态 |
| --- | --- | --- | --- | --- |
| `0f2a588d107343d8905afd6831056df3` | 2026-11-16T09:32 | — | ~8 s | `unknown_outcome` |
| `14e5f18e09be4cdf8e92f636dcd9cc31` | 10:19:34.439Z | 10:19:42.474Z | 8.03 s | `unknown_outcome` |

回执：

```json
{"status":"unknown_outcome","stage":"executing_feature_plan",
 "message":"Native worker exited 3221225477 without a result; inspect Creo before retrying"}
```

`3221225477 = 0xC0000005`（访问冲突）。两次 `native.log` 尾部**逐字相同**：

```
PHASE=execute_export
PROGRESS index=1 total=1 op=export label=- state=start elapsed_ms=4878 since_start_ms=4878
OPERATION_INDEX=0 INPUT={"format":"stl","op":"export"}
PHASE=export
ProPartTessellate((ProPart)board, 0.05, 0.1, PRO_B_FALSE, &surfaces)=0
ProArraySizeGet((ProArray)surfaces, &n)=0
```

两行的 `=0` 是调用返回码（`PRO_TK_NO_ERROR`），不是 `n` 的值。即剖分与取数组大小都成功返回，随后在遍历/写盘/释放剖分数据时崩溃，日志来不及写下一条。

- **导出通道整体不可用**：小零件 STL 成功。

## 原登记假设与建议修法（非已证根因）

主要假设：`ProPartTessellate` 的弦高 `0.05`、角容差 `0.1` 是硬编码常量，对 78 m 长、近百平方米双曲率外形会产生远超预期的三角面规模，`ProPartTessellate` 仍返回成功（可能是延迟求值或分配在后续步骤失败），随后在一次大块分配或越界写时触发访问冲突。第三个实参 `PRO_B_FALSE` 的语义（绝对/相对弦高）未核实；若它是"相对"，则该容差随模型尺寸放大，问题更可能在三角面数量之外的数组管理上，需要先确认。

按优先级建议：

1. **容差按尺度缩放或开放为参数**：以包围盒对角线为基准（例如 `chord = max(0.01, diag * 1e-6)`），或给 `export` 加 `tolerance_mm` 入参，并在回执里回显实际使用的容差与预估三角面数。
2. **流式写盘**：逐面剖分、逐面写文件，不要在内存里攒一个 `ProArray` 后再统一遍历；这同时消除了"数组过大"这一类失败模式。
3. **加空指针/尺寸判定与可诊断的失败码**：`ProArraySizeGet` 返回后先判 `surfaces == NULL` 与 `n == 0`，异常时回 `PRO_TK_*` 而不是继续解引用；崩溃能让客户端拿到 `unknown_outcome`，但拿不到原因。
4. **在遍历前补一条日志分界**：例如 `TESSEL ok n=%d, begin write`，下次崩溃就能确定是遍历、写盘还是释放。
5. 短期绕行：需要网格时先导 STEP 再在外部剖分——本次的曲面偏差复核就是这么做的（STEP 里带原始 NURBS，精度还高于三角网格）。

## 历史崩溃后的恢复操作（记录不授权后续自动执行）

1. 崩溃会使 Toolkit 校验被作废，下一次任何导出直接返回
   `Creo is not ready (timeout): Toolkit verification was invalidated by a subsequent failure`，且不排队任何作业。
2. 必须先调用 `creo_session_status` 做一次显式探测（本次两次都是探一次即恢复，`toolkit_code=0`）。
3. 模型进入 `unknown_outcome` 保护，不能重放原计划。用 `creo_reconcile_model(mode="inspect")` 取 `evidence_token`，再 `mode="apply", action="restore_baseline"` 清理；本次两次恢复分别为 `32bcd93fc9144083aec95f0adfde058b`、`e687dce8073f4cf6b6bff8bc657ae5be`，**revision 保持 8、`bulb_bulged.prt.9` 的 SHA256 `c1e810195be25aed34b4ba2fd4813c3fcbaa099ec0cc03794cffae06b4b35df3` 未变**。
4. `ack_no_mutation` 对 `unknown_outcome` 不可用（回执明确 "Only a failed model can acknowledge zero mutation"），所以只能走 `restore_baseline`；若希望"只读导出崩溃不进入保护"，需要单独设计只读作业的失败语义。

## 同批发现的其它接口问题（记录备查，未单开卡）

- **`plan_file` 只接受纯 operations 数组**：传 `{"operations":[…]}` 会被拒，客户端只收到 `Error executing tool`，没有可读原因，排查成本高。建议把 `plan_files.load_plan_operations` 的类型错误透出到回执。
- **`creo_execute_plan` 回显过大**：响应对整份归一化 operations 做回显，单个 12 操作的计划就超过单页 32 KiB 预算，必须分页读。
- **`export(jpeg)` 对 14 m 形体不可判读**：`preview.status=written`、`view_matrix_matches=false`，视图没有按模型尺寸 refit，14 m 长的形体被压成很小一块，无法用于目视检查曲面质量。建议 `refit` 后再栅格化，或按包围盒自适应视图矩阵。
