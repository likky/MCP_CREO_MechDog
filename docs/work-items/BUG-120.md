# BUG-120：Creo 10 球鼻艏创建流程依赖不支持的边界混合元素树

## T2-B 实机读数（2026-11-18，Creo 10 上完成，证据已核对）

证据：`docs/validation/bug120-t2b-creo10-2026-11-18/`（4 个 job 目录的 `job.json` / `native_result.json` / 日志）。
模型：`t2b_probe_01`，`feature_id=40`（XY，线长 120）、`feature_id=46`（XZ，线长 80），`saved_file_reloaded_and_verified=true`。

**定案事实：一条直线回答两条曲线**

| 特征 | 曲线 | composite | `ProCurveTypeGet` | 长度 |
|---|---|---|---|---|
| 40 | 43 | **true** | 41 | 120.0 |
| 40 | 45 | false | 2 | 120.0 |
| 46 | 49 | **true** | 41 | 80.0 |
| 46 | 51 | false | 2 | 80.0 |

即：每个草图曲线自带一条**单成员复合曲线（41）**与一条真实曲线（2），长度相同、都 `readable`、`length_code=0`。上次 T2 报的 `type=62/25` 是 inspect 的另一套数值空间，以本次 `ProCurveTypeGet` 为准。

**据此改了 D2 的选择规则**（`native/panel_references_sdk.h`）：调用方只给 feature、不给 curve id 时，取该特征下**唯一的非复合曲线**；若无或多于一条，报 `PANEL_CURVE_NONE_NON_COMPOSITE` / `PANEL_CURVE_AMBIGUOUS` 并拒绝，**不按 id 顺序猜**，也绝不把复合曲线当成"那条曲线"。若调用方给了 curve id，保持精确匹配（原有行为不变）。

**仍未解决（T3 前必须定）**：Blend 路线用 `all_curves_in_feature` 链选择，它选中的可能是那条 composite。面板路线到底该按 feature 选（走本次规则）还是按复合曲线选，必须在真实对话框里看 `PRO_SELECT_*` 的实际落点才能定。

**两个接口缺口（已记录，未修）**：①`curve_facts` 只在 `detail=full` + `section=operations_result` 出现，compact 视图看不见；②`native_section.open_end_samples` 坐标与输入 UV 不一致（`matrix_identity=false`、`uv_mapping=location_matrix`），尚无解释。

验证：`bridge.py build` EXIT=0；`tools/test_panel_references.py` 通过（`all rules hold`）；`test_panel_selection_protocol` 19 项通过。

## T2-B 与草图契约修补（2026-11-18，离线完成，待实机复核）

针对 T2 暴露的两个问题，改造了 `creo_create_sketch` 的返回值（`native/generic.cpp`）：

- **`feature_id`**：草图结果现在带新建草图自己的特征 id（T2 里只能事后从 `inspect` 反查 40/46，客户端拿不到自己刚建的对象）。
- **`curve_facts`**：新建草图**逐条**返回它拥有的曲线事实，每条含 `id`、`readable`、`type`（数值）、`type_code`、`composite`、`length_mm`、`length_code`。数据来自 `ProFeatureGeomitemVisit(PRO_CURVE)` + `ProCurveInit` + `ProCurveTypeGet` + `ProCurveLengthEval`，与面板路线同源，**不取自请求**。

这样 T2-B 不需要新工具、新作业类型：在那台机器上重跑同一条建草图流程，直接看 `curve_facts` 就能回答"一条直线为何两个 `type=62`"——若两条 `composite=false`、长度相同，说明是同一条线的两个表达；若长度不同或 `readable=false`，说明其中一条不是可选曲线，D2 必须按长度/类型筛掉它。

验证：`bridge.py build` EXIT=0；Creo 10 SDK 编译对照 `--full` **4/4 exit 0**（新字段在目标 SDK 下同样成立）；全量单测 **3987 项通过**（新增 2 项草图契约守卫、3 项此前接线守卫）。**未做**：没有任何一次真实 Creo 运行读过 `curve_facts`，所以"两条 62 的语义"仍是待答问题，不得写成已解决。

## T2 实机结果（2026-11-18，Creo 10 上只读枚举）

证据：`docs/validation/bug120-t2-creo10-2026-11-18/`（WorkBuddy 原始回报 + 一份 `feature_geometry` 样本）。
会话：`connected=true`、`release_numeric=42`、`Creo 10.0.0.0`、worker `source_digest` 校验通过；模型为新建空零件 `t2_curve_probe`，最终 `revision=4`、`saved_file_reloaded_and_verified=true`。

**已验证成立**（这些以前只是假设）：
- 特征→曲线可枚举：草图 40 → `43,45`；草图 46 → `49,51`；两组不重叠（`curve_ids_unique=true`）。
- 基准面（RIGHT 1 / TOP 3 / FRONT 5）下**没有** `type=62` 的曲线条目，只有 1 条 `type=5`（面本身）。所以"基准面不会被当成曲线源"成立——但**判定必须按曲线类型**，不能按 `geometry_items` 是否为空（我原先给的核对口径"应为 0 条"是错的，基准面本来就有 1 条面条目）。

**两个必须记住的偏差**（直接影响 D2）：
1. `creo_create_sketch` 成功返回里**没有 `feature_id`**，只有 `surface_id`（=支撑基准面的几何 id，草图1=6/FRONT、草图2=4/TOP）。草图特征 id（40/46）只能事后从 `inspect` 的 `features` 或 `aliases` 取。这是 MCP 契约的真实缺口，客户端无法直接引用刚建的草图。
2. **一条直线在 `feature_geometry` 里产生 2 条 `type=62`（如 43、45）加 1 条 `type=25`（44）**。若一个截面按"一条曲线"处理，真机上就会面对 2 个候选 id；`type=62` 是否等于 `PRO_CURVE` 也无法由 `creo_lookup_constants` 确认（它只返回 `PRO_CURVE_TYPE_*`）。

**仍未验证**：两条 `type=62` 的语义（同一条线为何两条）、长度/开闭性、`PRO_SELECT_TOGGLE` 实际效果、受限 Done 宏、`AfterTerminal`/`OuterDrain` 时序——全部属 T3 与 T2-B。

**结论口径**：T2 只证明"能枚举、归属正确、基准面不误判"，不证明"曲线引用解析可用"。D2 的 `curve_id` 选择规则必须先用一次只读探针（T2-B）把"一条线两条曲线"弄清楚，否则 T3 会在第一步就选错曲线。
