# BUG-144 打包单测读取上一轮报告，发布门禁接受陈旧成功报告

分类：**已有修复但待验收**

类型：缺陷  
优先级：P1  
状态：离线修复已实施，发布验收待续  
目标版本：未排期，优先纳入下一次 PATCH

## 来源与现象

- 2026-11-21 的 0.35.2 外部反馈（主干 `b702b6c`，Windows 10 x64、Python 3.13.14、Creo 9.0.0.0 SDK）。第一轮全量单测有 1 个错误，第二轮串行重跑有 3 个打包用例失败。第二轮拒包信息引用第一轮的 `errors=1`。反馈中的对照实验只切换共享报告的 `success`，同组用例随之通过或失败。报告同时记载原 `runner.log` 占用未再出现，以及两项离线验收脚本通过。关联 [BUG-137](BUG-137.md) 与 [BUG-138](BUG-138.md)。
- 本轮核对基线为 0.35.4 / `98c598f89d06121e5f1b87ab9c3a90ff67227c6e`，干净工作树，Windows、Python 3.12.10。将该版发布说明和发布记录复制到临时目录，调用 `_unit_test_claim_problems`。缺失和失败报告被拒绝，有效成功夹具被接受，`version=0.1.0`、`timestamp=1` 的陈旧成功夹具也被接受。本轮复核限门禁函数，端到端打包和全量单测留待实施阶段。
- 原附件 SHA256 为 `79ef0fd5f767db990872b2e573c13f9e58ea669959e2c5fe46724594cf79223c`。

## 原因

`tools/test_unit.py` 在全量结束后才写报告。运行期间，`SeedPackagingGateTests` 从真实源码根运行 `tools/package.py`，后者通过 `validate_release_records(..., root=ROOT)` 读取同一目录的 `build/unit_test_report.json`。门禁仅检查 `success is True`，所以缺失或失败的旧报告导致假失败，陈旧成功报告也能支撑当前版发布声明。默认输出用例还在仓库父目录使用固定文件名，并在退出时删除该路径，测试并跑或已有同名产物时存在额外冲突。

## 实施顺序

1. **复现整条链路。** 在独立检出或临时源码副本中，冻结相同源码和发布记录，分别放置缺失、失败、成功报告，运行 `SeedPackagingGateTests` 的显式输出、默认输出和 stage 正例，保留退出码和 stderr。诊断夹具写入的报告只用于测试。
2. **隔离打包用例。** 为打包 CLI 测试建立临时源码根、报告和输出父目录，复用现有夹具和打包清单，保留实际的种子、发布记录和四附件校验。让默认输出仍由 CLI 自行计算，并落在夹具目录。覆盖真实源码根有失败报告和同名输出的对照，核对测试只访问和清理自己的路径。报告路径如需注入，只选择证据文件，保留整套验证。
3. **绑定正式发布证据。** 保留 `test_unit.py` 现有统计字段和常用入口。按独立运行路径或运行标识关联测试与正式构包，复用报告已有的版本和源码指纹，验证其与当前受测源一致。正式流程只接受本轮完成的结果。用同目录临时文件和原子替换发布终态，处理超时、中断及并跑，防止旧报告被当作当前结果。时间戳用于诊断。发布记录有全量通过声明时，给出缺失、失败、不可读、未完成或身份不匹配的具体原因，并在写出正式 ZIP、校验文件和 stage 之前拒绝。远端仅有 ZIP 的检查继续验证包内记录及附件，解压目录的测试证据单独记录。
4. **回归与交付。** 用修复后的 Windows 测试结果更新工作卡。若进入正式发布，按项目发布规则选择未发布的 PATCH，在实际发布源码上重新生成报告及四个附件，并核对标签、Release 和 SHA256。

- 发布时用新路径运行 `tools/test_unit.py --report`，再以 `tools/package.py --unit-report` 使用这次结果。以前一轮文件名重跑会被拒绝。本轮报告未完成时，门禁不读取共享报告或其他轮次的报告。
