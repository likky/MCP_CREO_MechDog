# BUG-144 打包单测读取上一轮报告，发布门禁接受陈旧成功报告

分类：**已交付 0.35.5**

类型：缺陷  
优先级：P1  
状态：已交付 0.35.5（运行状态绑定、打包测试隔离、写产物前拒绝均已实现；修复前复现与三条打包路径回归通过）  
目标版本：0.35.5（已交付）；其他环境按反馈补录

## 来源与现象

- 2026-11-21 的 0.35.2 外部反馈（主干 `b702b6c`，Windows 10 x64、Python 3.13.14、Creo 9.0.0.0 SDK）。第一轮全量单测有 1 个错误，第二轮串行重跑有 3 个打包用例失败。第二轮拒包信息引用第一轮的 `errors=1`。反馈中的对照实验只切换共享报告的 `success`，同组用例随之通过或失败。报告同时记载原 `runner.log` 占用未再出现，以及两项离线验收脚本通过。关联 [BUG-137](BUG-137.md) 与 [BUG-138](BUG-138.md)。
- 本轮核对基线为 0.35.4 / `98c598f89d06121e5f1b87ab9c3a90ff67227c6e`，干净工作树，Windows、Python 3.12.10。将该版发布说明和发布记录复制到临时目录，调用 `_unit_test_claim_problems`。缺失和失败报告被拒绝，有效成功夹具被接受，`version=0.1.0`、`timestamp=1` 的陈旧成功夹具也被接受。本轮复核限门禁函数，端到端打包和全量单测留待实施阶段。
- 原附件 SHA256 为 `79ef0fd5f767db990872b2e573c13f9e58ea669959e2c5fe46724594cf79223c`。

## 原因

`tools/test_unit.py` 在全量结束后才写报告。运行期间，`SeedPackagingGateTests` 从真实源码根运行 `tools/package.py`，后者通过 `validate_release_records(..., root=ROOT)` 读取同一目录的 `build/unit_test_report.json`。门禁仅检查 `success is True`，所以缺失或失败的旧报告导致假失败，陈旧成功报告也能支撑当前版发布声明。默认输出用例还在仓库父目录使用固定文件名，并在退出时删除该路径，测试并跑或已有同名产物时存在额外冲突。

## 实施顺序

1. **复现整条链路。** 在独立检出或临时源码副本中，冻结相同源码和发布记录，分别放置缺失、失败、成功报告，运行 `SeedPackagingGateTests` 的显式输出、默认输出和 stage 正例，保留退出码和 stderr。诊断夹具写入的报告只用于测试。
2. **隔离打包用例。** 为打包 CLI 测试建立临时源码根、报告和输出父目录，复用现有夹具和打包清单，保留实际的种子、发布记录和四附件校验。让默认输出仍由 CLI 自行计算，并落在夹具目录。覆盖真实源码根有失败报告和同名输出的对照，核对测试只访问和清理自己的路径。报告路径如需注入，只选择证据文件，保留整套验证。
3. **绑定正式发布证据。** 保留 `test_unit.py` 现有统计字段和常用入口。按独立运行路径或运行标识关联测试与正式构包，复用报告已有的版本和源码指纹，验证其与当前受测源一致。正式流程只接受本轮完成的结果。用同目录临时文件和原子替换发布终态，处理超时、中断及并跑，防止旧报告被当作当前结果。时间戳用于诊断。发布记录有全量通过声明时，给出缺失、失败、不可读、未完成或身份不匹配的具体原因，并在写出正式 ZIP、校验文件和 stage 之前拒绝。远端仅有 ZIP 的检查继续验证包内记录及附件，解压目录的测试证据单独记录。
4. **回归与交付。** 用修复后的 Windows 测试结果更新工作卡。若进入正式发布，按项目发布规则选择未发布的 PATCH，在实际发布源码上重新生成报告及四个附件，并核对标签、Release 和 SHA256。

## 实现与证据（0.35.5）

修复前复现：在 detached worktree（`5b32ef7`）写入 `success=false` 的陈旧 `build/unit_test_report.json`，直接运行旧版 `SeedPackagingGateTests` 显式输出用例。结果 FAIL / exit 1，stderr 为 `[release-gate] 0.35.4 unit test report: success=False, tests_run=1, failures=1, errors=0, skipped=0` 与 `Release record gate rejected this package: - source tree: release record claims 全量 unittest 通过 but build/unit_test_report.json reports success=False ...`，证明旧代码读取工作区共享报告而非本轮证据。输出存档 `build/bug144_repro_old_failure.txt`。

实现：

- `src/creo_mechdog/unit_evidence.py`（新增）：运行前原子写 `build/unit_test_run.json`（`status="running"`、`run_id`、PID、版本与源码身份），结束后原子置 `completed`/`interrupted`；`O_EXCL` 运行锁只在持锁 PID 已死亡时接管。报告与状态都用 `.tmp` + `os.replace` 发布，不暴露半写文件。
- `tools/test_unit.py`：先取运行锁（占用时 exit 3），运行前 `start_run`，异常时 `interrupt_run`，结束后原子写带 `run_id` 的报告并 `finish_run`，`finally` 只释放自己的锁。
- `src/creo_mechdog/release_integrity.py`：新增 `UNIT_EVIDENCE_ENFORCED_FROM = (0, 35, 5)`。自 0.35.5 起，`全量 unittest 通过` 声明必须由状态文件与报告共同支撑：状态存在、schema 一致、`completed`、`success=true`、版本一致、报告与状态 `run_id` 相同、两侧 `source_status="complete"`、报告与状态指纹都等于当前受测源 `local_provenance` 指纹、`tests_run>0`。更早版本维持仅 `success=true`，已发布记录逐字节不变。
- `tools/package.py`：新增 `--source-root`（测试隔离源码根，默认当前检出）与 `--unit-report`（只注入证据文件路径，默认 `<source-root>/build/unit_test_report.json`）；发布记录门禁移到写 ZIP、sidecar 与 stage **之前**，默认输出落在源码根父目录。
- 测试：新增 `tests/unit/test_unit_evidence.py`（状态往返、interrupt、旧轮次不能覆盖新一轮、活/死 PID 锁、原子写无 `.tmp`；0.35.5 下七类拒绝：缺状态、复用上轮成功、`run_id` 不符、指纹不符、失败轮次、版本不符、`tests_run=0`）。`tests/unit/test_release_integrity.py` 的 `SeedPackagingGateTests` 改为在临时 `checkout` 副本上打包，`run_package` 固定传 `--source-root`，覆盖显式输出、默认输出、stage 三条正例与既有输出/非空 stage/缺证据/失败证据拒绝；原有 v0.35.4 下 11 项通过、2 项严格绑定用例因低于生效版本跳过，升版 0.35.5 后按新契约运行。

未验：外部反馈环境（Windows 10 / Python 3.13 / Creo 9 SDK）复跑；`runner.log` 子进程导入失败观察项未在本轮复现。解压源码包的独立全量验收：在 `build\extract-0.35.5` 用独立 venv（仅 `requirements.lock.txt` 依赖 + editable 安装解压副本）运行 `unittest discover -s tests`，`Ran 4311`、`errors=3`、`skipped=14`；3 项失败均为解压环境限制（2 项缺本机 `config.json`、1 项长路径触发 Windows MAX_PATH），同一源码在主检出环境 4319 项全通过。
