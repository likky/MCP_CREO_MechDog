## 二、核心问题一：全量单测 3 个 teardown errors 逐字复现（上轮未修）

### 1. 现象：与 0.26.0 反馈一字不差

`build/unit_test_report.json`（0.31.1）：

```json
{"version":"0.31.1","tests_run":4078,"success":false,"failures":0,"errors":3,"skipped":4,
 "duration_seconds":1517.36}
```

3 个错误全部在 `InspectionOnlyAdmission`，与 0.26.0 上轮反馈的 3 个测试方法完全相同：

```text
ERROR: test_a_new_model_is_never_downgraded (...InspectionOnlyAdmission...)
ERROR: test_expected_revision_stays_optional_for_the_downgraded_plan (...)
ERROR: test_export_only_plan_is_admitted_without_a_saved_baseline (...)
```

统一堆栈，测试逻辑已通过，失败在 `TemporaryDirectory` 清理：

```text
File "tempfile.py", line 935, in _rmtree
File "shutil.py", line 790, in rmtree
PermissionError: [WinError 32] 另一个程序正在使用此文件，进程无法访问。:
  '...\MCP_CREO_MechDog\.tmp\bug009_ydmvq3fh\jobs\36a796b7017b4e7aa1d2e1e481ed1184\runner.log'
```

### 2. 根因（0.31.1 代码仍未改）

`bridge.py:1613-1622`（上轮为 1476，仅行号漂移）仍是真实 `Popen`，让 worker 继承 `runner.log` 文件句柄：

```python
with (directory / "runner.log").open("ab") as log:
    proc = subprocess.Popen(
        [sys.executable, str(ROOT / "bridge.py"), "run-job", job_id],
        stdout=log, stderr=subprocess.STDOUT, ...)
```

`tests/unit/test_inspection_only_admission.py:108-132` 的 `run_job()` 只 patch `bridge.subprocess.run`（synthetic worker），**没有 patch `subprocess.Popen`**：

```python
with patch.object(bridge, "build_native", ...), \
     patch.object(bridge, "native_environment", ...), \
     patch.object(bridge.subprocess, "run", side_effect=run):
    bridge.run_job(created["job_id"])
```

于是真实 `Popen` 启动的 worker 在测试清理临时目录时尚未退出，`runner.log` 句柄未释放 → WinError 32。单跑该类可通过但有 `ResourceWarning: subprocess ... is still running`，只在全量时序竞态下命中。

### 3. 作者处置情况

- 上轮反馈后，作者在 `docs/BACKLOG.md` 0.24.1 条目把该现象定性为“本机环境问题”（原文：“`unit.test_inspection_only_admission` 3 项在本机因 `.tmp` 下 `runner.log` 被占用（`WinError 32`）失败……属本机环境问题”），未立工作卡、未改测试或 `bridge.py`。
- `git log ef02f07..origin/main -- tests/unit/test_inspection_only_admission.py tests/unit/test_toolkit_channel.py bridge.py`：本跨版本区间内相关测试文件无修复提交。
- `RELEASE-0.31.1.md`：离线结果写“全量 unittest 4078 项通过（6 跳过）”，与本机 3 errors 不一致（跳过数 4 vs 6 亦不同，见 §四）。

## 三、核心问题二：`tools/` 独立验收脚本硬编码旧工具数，跨 6 版本必失败（上轮未修）

### 1. 现象

在**有 git**、有网络、环境完全正常的情况下运行项目自带验收脚本：

```text
$ python tools/test_update_check.py
{"success": false, "tool_count": 109, "update": null,
 "modeling": {"status": "not_requested"},
 "failure": "unhandled errors in a TaskGroup (1 sub-exception)"}
退出码 1
```

`creo_check_update` 本身正常（up_to_date），唯一失败点是工具数断言。

### 2. 根因：硬编码 + 异常掩盖双重缺陷

`tools/test_update_check.py:108`：

```python
assert capabilities["tool_count"] == len(tools) == 82
```

`tools/test_model_reconciliation.py:331`：

```python
assert capability["tool_count"] == 84
```

实际 `tool_count=109`（README / AGENTS 均以 `creo_capabilities` 为准）。硬编码始于 2026-10-14 `da57ab9`（FEAT-020，当时工具数 82），此后工具数 82→95→102→104→107→108→109 一路增长，两处断言从未更新。0.26.0 上轮反馈时实际为 108，本轮 109，断言仍停在 82。

更糟的是断言失败被包装成 `unhandled errors in a TaskGroup (1 sub-exception)`，真实断言信息在 stdio 输出中不可见，用户/门禁只知道“失败”，不知道是工具数过时——这与“负例红字与真实失败同形”是同一类可观测性问题。

`docs/UPDATE_CHECK.md:3` 仍写“工具总数为 82”，文档与断言同源过时。

### 3. 为什么跨 6 个版本未暴露

- `tools/dev_check.py` 只跑 Ruff/clang-format 与 `tools/test_unit.py`（第 253 行）；
- CI `.github/workflows/checks.yml` 只跑 `tools/check_backlog_counts.py` 与 `tools/dev_check.py`；
- 二者**都不运行 `tools/` 下的独立验收脚本**。因此 `test_update_check.py` / `test_model_reconciliation.py` 自 0.3.0 引入硬编码后从未被自动门禁覆盖，即使每次都必失败也不影响发布。

### 4. 作者处置情况

`git log ef02f07..origin/main -- tools/test_update_check.py tools/test_model_reconciliation.py` 为空：0.26.0 反馈后跨 6 个版本对这两个脚本零改动。DEV-066 台账仍为“部分交付，剩余待规划”，DEV-075 验收记录提到 `test_update_check.py` 只作为“工作区开头已有文件”被保留，未处理其硬编码。

## 四、次要观察（非核心，供参考）

1. **启动锁警告**：MCP 冒烟与 `test_update_check.py` 运行时出现 `WARNING:creo_startup:Startup coordination lock access failed`（`creo_startup.py:898`，`CoordinatorLockError` 分类为 `lock_error`）。该警告在 0.26.0 已存在，属本机已有 Creo/启动协调器占用锁的环境行为，代码已明确分类并保留现场，不计为项目缺陷。
2. **`.lock` 残留放大拉取失败**：本次前台 `git fetch` 被工具超时 SIGTERM 后，留下 `main.lock` 等 5 个 `.git/refs/**/*.lock`，导致后续 fetch 报 “Another git process seems to be running”。清理锁后恢复。这是工具超时与 git 的交互，非项目缺陷，但建议在文档提示“大仓 fetch 用后台方式”。
3. **发布记录跳过数不一致**：`RELEASE-0.31.1.md` 写“4078 项通过（6 跳过）”，本机报告为 4 跳过（两项 MSVC helper 不可用、两项 BUG-130 归档 job 不在本机）。跨环境差异可接受，但“通过”口径应同时给出 errors 与 skipped 的真实数字，避免用户以为本机也全绿。
4. **`docs/COMPATIBILITY.md` 版本归属说明停留在 0.24.0/0.24.1**，与当前 0.31.1 相差 7 个版本；文中“当前”字样依赖各节写作时点说明，但对新用户不友好。

## 五、修复建议（沿用上轮，优先级 P1）

1. **隔离 `Popen`（核心问题一）**：`ToolkitChannel.run_job` 的测试应 patch `subprocess.Popen`（或让 `bridge.py` 的 worker 启动走可注入的工厂），使测试不启动真实子进程；或在测试 `run_job` 后 `proc.wait()` 再退出 `TemporaryDirectory`。发布门禁应要求 `tools/test_unit.py` 报告 `success=true` 才能写“全量通过”。
2. **去除硬编码工具数（核心问题二）**：
   - `tools/test_update_check.py:108` 改为 `assert capabilities["tool_count"] == len(tools)`，另设与版本解耦的一致性检查；
   - `tools/test_model_reconciliation.py:331` 同样去除 `== 84`；
   - `docs/UPDATE_CHECK.md:3` 的“工具总数 82”改为“以 `creo_capabilities` 返回为准”；
   - 断言失败不要把原始异常吞进 `TaskGroup`，应显式打印断言上下文。
3. **扩大门禁覆盖**：在 `dev_check.py` / CI 增加一步，至少做 `tools/test_update_check.py`、`tools/test_model_reconciliation.py` 的离线可运行性检查（不依赖 Creo），从机制上防止独立验收脚本腐化。
4. **发布口径**：发布记录把“4078 项通过”改为“4078 项运行，X 通过 / Y 失败 / Z 错误 / W 跳过”，并标注受测工作区是否干净、是否为真实升级工作区。
