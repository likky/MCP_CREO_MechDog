# CREO MCP 反馈：启动校验 2 秒探测超时 + 预算耗尽后丢弃已成功探测，导致 109 个建模工具全部拒单

- 反馈日期：2026-11-20
- 运行版本：**0.31.1**（本机实测复现；MCP 自报最新版 **0.32.0**，本机未安装、未在 0.32.0 上验证）
- Creo：Creo 9.0.0.0（release_numeric = 41），`D:\CREO\Creo 9.0.0.0`
- 宿主：Windows 10 19045，MCP 以 stdio 方式接入
- 影响：**109 个工具全部不可用**（`creo_capabilities` 报 `tool_count: 109 / enabled_tool_count: 109`），包括最基础的 `creo_new_part` 与 `creo_execute_plan`

---

## 一、核心问题（一句话）

启动协调器在**原生 worker 与 Creo 都已就绪、独立探测 `connected:true`** 的情况下，用**硬编码 2 秒连接超时**反复探测，永远拿不到成功；300 秒总预算耗尽后，即便最后一轮探测已经成功，也**只发布 `timeout`、不发布 `ready`**，于是 `require_ready()` 永久拒绝一切建模作业。

---

## 三、关键证据

### 3.1 连接本身是好的（不是 Creo、不是 SDK、不是许可证、不是 worker）

同一时刻调用 `creo_session_status`：

```json
{
  "connected": true,
  "connection_state": "connected",
  "toolkit_code": 0,
  "disconnect_code": 0,
  "worker_exit_code": 0,
  "worker_build_identity": {"identity_status": "verified", "worker_sha256": "8b69c4e1...c4b6"},
  "release_numeric": 41,
  "toolkit_hint": "Toolkit connection verified",
  "live_probe": {"performed": true, "busy": false, "queued": false}
}
```

`creo_check_environment` 同样全绿（`ready_to_build: true`）。也就是说：**工具链、SDK、worker、Creo 会话、通道全部正常，唯独准入开关不打开。**

### 3.2 每次「building_worker」并不在构建

`build/` 内产物在整个 40 分钟里没有任何变化：

```
creo_worker.exe            14:50
blend_sync_build.json      14:50
blend_loader_build.json    14:50
source.sha256              14:50
generate_constants.log     18:15 / 18:22（仅每次周期开头被重写）
```

构建期间无任何编译器进程（cl/link）。所以状态里那句 "Building/verifying the native worker" 在此期间**是误导性的**。

### 3.3 协调器探测用的是 2 秒超时（代码定位）

`creo_startup.py`：

```python
# 1216 行（连接循环内）
native = bridge.session_status(connect_timeout_seconds=2, build_worker=False)
```

而服务自己的只读探测用的是 **9 秒**预算，我手动调用时用的是 30 秒默认值——两者都成功。也就是说，本机 Toolkit 异步握手耗时在 **2 s 与 9 s 之间**：9 s 成功、2 s 永久失败。

`bridge.session_status()` 对 `probe_timeout` 的处理是**直接返回**，不重试：

```python
except subprocess.TimeoutExpired:
    return record_channel_health(False, connection_state="probe_timeout", ...)
```

### 3.4 预算耗尽后，成功的探测被丢弃

`creo_startup.py` 的连接循环：

```python
while not self._stop.is_set() and time.monotonic() < deadline:   # 1192
    ...
    if native.get("connected"):
        self._publish("ready", "Toolkit connection verified; modeling is available", ...)  # 1235-1245
        return
# 循环因 deadline 到期退出后走 timeout 分支
```

循环条件先失败 → 根本不再执行循环体里的成功判定 → 即使上一轮 `native.connected` 已经为 `true`，仍发布 `timeout`。第 1、2 周期返回体里 `state: "timeout"` 与 `native.connected: true` 同时出现，就是这个分支的直接产物。

### 3.5 相位标签在连接阶段不推进

```python
# 1157-1164
with bridge.toolkit_lock(operation="startup_build"):
    self._publish("building_worker", "Building/verifying the native worker", ...)
    bridge.build_native()
break
# 之后直接进入连接循环（1189-1245），全程不再 publish 任何相位
```

`build_native()` 返回后没有任何状态更新，于是整个连接阶段（最长 300 秒）对外仍显示 `building_worker`，且 `updated_at` 冻结在周期起点（实测 `updated_at` 恒为 `10:15:49.942`，而 `started_at` 也是 `10:15:49.856`）。调用方无法区分「在建」和「在连」，`phase_remaining_budget_seconds` 与真实进度完全脱节。

### 3.6 循环无退避，握手可能自相争抢（待作者确认的次要假设）

连接循环里每次失败后**没有任何 backoff**，300 秒内可产生数百次探测；每次探测都要起一个 `creo_worker.exe` 并完成 procmgr 握手。两个周期里**最后一次探测都成功了**（`verified_at` 与 `timeout` 发布时刻同为 10:12:27 / 10:21:44），而循环一停、我下一句 `creo_session_status` 也是立即成功。这与「通道被自己的高频探测占满、循环停止后立刻恢复」的现象一致。

进程侧已排除泄漏：`nmsd / pro_comm_msg / parametric / xtop` 各只有 1 个，没有堆积的残留握手进程。

建议：探测失败改为指数退避（如 1→2→5→10 s），并在每次探测前后检查 `toolkit-owner.lock`，避免自身竞争。

### 3.7 重试没有收敛性

`timeout` 后 `retry_allowed: true`，但 `retry` 只是重跑同一个 300 秒循环：先 2 秒探测、再耗尽预算、再发布 `timeout`。四个周期累计约 25 分钟，没有任何一次把准入打开，也没有任何降级路径（例如「已有一次 30 秒探测成功即可放行」）。

## 四、上一轮反馈的更正（重要，请勿沿用旧结论）

上一轮（2026-11-20 上午）我曾提交过一份「native worker 依赖 ucore68.dll 不在 PATH」的反馈。**本次实测证明该结论是错的**，请不要按它改代码：

- `creo_worker.exe` 的 27 个导入依赖逐个核对，**全部可解析**：`ucore68.dll` 命中 `Common Files\x86e_win64\lib`（`native_environment()` 已把 `x86e_win64/lib`、`x86e_win64/obj`、`libs/dfor/lib` 三段加入 `PATH`）；其余 26 个中只有 12 个 `api-ms-win-crt-*` 不在磁盘上——这些是 UCRT 的 API set 虚拟名，由加载器映射，本来就没有对应文件。
- `worker_build_identity.identity_status` 现在稳定为 `verified`，`worker_exit_code: 0`。

**由此暴露一个新的可观测性缺陷**：`build/toolkit_health.json` 里长期保留

```json
"worker_build_identity": {"identity_status": "invalid_build_info", "worker_exit_code": 3221225781}
```

`3221225781 = 0xC0000135 (STATUS_DLL_NOT_FOUND)`，但它**没有时间戳、没有产生它的探测环境标识**，且与当前 `verified / 0` 的结论并存。这份陈旧证据会把人直接引向错误的根因（本人即因此误判一轮）。建议：随每条身份证据记录 `observed_at` + `env_fingerprint`（至少 PATH 的哈希），并在身份已 `verified` 后不再并列展示历史失败码。

## 五、影响范围

- 全部 109 个工具不可用，包括只读之外的一切写操作：`creo_execute_plan`、`creo_new_part`、`creo_sketch_*`、`creo_pad/revolve/hole/round/chamfer`、`creo_assemble_component`、`creo_save_document`。
- 反而**只读探测可用**（`creo_session_status`、`creo_check_environment`、`creo_capabilities`），造成「看起来一切正常、就是不能建模」的错觉。
- 冷启动（MCP 自动拉起 Creo）场景更严重：Creo 冷启动本身需要 6~8 分钟，与 300 秒预算天然冲突。

## 六、修复建议（按优先级）

1. **P0｜探测超时可配置且不低于实测延迟**：把 `creo_startup.py:1216` 的 `connect_timeout_seconds=2` 提到配置项（如 `creo_probe_timeout_seconds`，默认 ≥ 10），或直接取 `settings.timeout` 的一部分；`probe_timeout` 不应一次即判死，应在预算内重试。
2. **P0｜成功的探测必须能落地**：把 `if native.get("connected")` 的判定移到循环之外（循环结束后再判一次），或改为「预算耗尽前最后一次探测成功 → `ready`」。当前实现会把已到手的连接丢掉。
3. **P1｜连接阶段要有自己的相位**：`build_native()` 返回后立即 `publish("connecting", ...)`，并让 `updated_at` 随每次探测刷新，使 `phase`/`updated_at` 能反映真实进度。
4. **P1｜总预算自适应**：300 秒固定预算在冷启动 Creo 的机器上不可能满足；建议 `startup_total_budget_seconds` 可配，或按「准备耗时 + 连接预算」两段分别计时（现在 `preparation` 与 `connect` 共用同一个 deadline）。
5. **P2｜准入降级**：当 `creo_session_status` 在最近 N 秒内返回过 `connected: true` 时，`require_ready()` 应允许放行（或提供 `creo_startup_status(force_ready=true)` 的操作员覆盖），避免「探测通过但准入不开」的死局。
6. **P2｜证据可归因**：`toolkit_health.json` 的 `worker_build_identity` 增加 `observed_at` 与 `env_fingerprint`；`identity_status=verified` 后清掉历史失败码。
7. **P3｜错误文案**：`"Creo is not ready (building_worker)"` 在构建早已结束时仍然出现，建议附上「最后一次探测的 `toolkit_code` / `connect_timeout`」两个字段，便于一线判断是超时还是 busy。
