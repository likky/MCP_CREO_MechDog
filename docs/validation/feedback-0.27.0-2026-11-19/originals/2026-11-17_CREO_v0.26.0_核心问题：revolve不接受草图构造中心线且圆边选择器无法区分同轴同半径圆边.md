# MCP_CREO_MechDog v0.26.0 问题反馈：revolve 不接受草图构造中心线 / coordinates 拒绝带构造几何的草图 / 圆边选择器无法区分同轴同半径圆边

- 反馈日期：2026-11-17
- MCP 版本：v0.26.0（CREO release numeric 41）
- 复现模型：M113 装甲车履带 Part6 驱动齿（TXT 附录 B `SK P06-01`、`SK P06-02`）
- 建模通道：仅 `creo_execute_plan`，几何 100% 来自 TXT 附录 B 的草图坐标
- 结论：三个独立缺陷，均已用 A/B 作业对照定位到具体阶段，均有可用规避手段，但都会让「只按 TXT 数据下发」的调用方无法直接完成任务

---

## 问题 1（高优先级）：revolve 无法使用草图内的构造中心线作为旋转轴，必须外部建 datum_axis 才能成功

### 现象

同一份 266 条实体的闭合截面（`SK P06-01`，4 条样条已离散为折线），仅旋转轴来源不同：

| 作业 | 轴来源 | 结果 |
| --- | --- | --- |
| `4b89de94935b43e5be42bc80e23b24d3` | 草图内构造线 `ln01`（起 (-54,0) 终 (54,0)，即 X 轴） | **失败** |
| `83209d76492b4355abfcd1dba6dd5882` | 显式 `datum_axis`（datum plane Y ∩ datum plane Z = X 轴） | **成功**，体积 10 851 508 mm³ |

失败作业的报错：

```text
Revolve feature creation failed (ProFeatureWithoptionsCreate=-1).
The closed profile must lie entirely on one side of the revolve axis and must not cross it;
entities may touch the axis.
The sketch must contain a centerline, or an explicit axis must be supplied, and the profile must be closed.
Detected native section: 1 closed contour(s), 1 contour(s), 266 entity(ies), 0 open end(s).
These counts do not identify the cause; the cause is not determined.
Sketch: 'p06_profile'.
```

### 关键证据：截面本身是干净的

失败作业的草图诊断（`creo_get_job` 返回的 `operations[0].profile` / `native_section`）：

```text
entity_count 266, contour_count 1, closed_contour_count 1, open_contour_count 0
max_endpoint_gap_mm 0.0, near_tolerance_pairs.total 0
native_section: closed_contours 1, open_ends 0, max_cluster_spread_mm 0.0,
                construction_entities 1, unsupported_entities 0
geometry_deviation.max_deviation_mm 2.84e-14
```

同一作业的 `native_section.construction_entities = 1`，成功作业为 `0`；除此之外两个作业的草图实体**逐点一致**（都是 266 条曲线，偏差 2.84e-14）。因此失败原因不是端点未焊接、不是截面不闭合、不是截面穿越轴线，而是「用草图自身构造中心线当轴」这条路径本身不可用。

### 与文档描述冲突

`src/creo_mechdog/references.py` 中 `RevolveAxis` 的说明明确支持这条路径：

```text
Omit axis (or pass null) to revolve about the sketch's own construction
centerline; that sketch must contain exactly one centerline.
```

`native/advanced.cpp` 的报错文案也写 "The sketch must contain a centerline, or an explicit axis must be supplied"，暗示两条路径等价，实际只有显式轴可用。

### 影响

TXT 附录 B 给出的旋转类草图（`SK P06-01`、`SK P06-04`）都自带构造中心线，这是源文档描述回转体的自然方式。调用方按文档「省略 axis」时必然失败，且报错把原因指向截面（不闭合 / 穿越轴线），排查方向被误导。

### 临时规避（已生效）

先建 `datum_axis`，再用 `axis: {kind: "datum_axis_feature", label: ...}` 引用；同时把草图内所有 construction 实体剔除（参见问题 2）。

### 建议

1. 修复 `axis` 省略时的构造中心线路径，或
2. 在省略 axis 且草图含构造中心线时直接返回明确的 `unsupported` 错误，不要落到 `ProFeatureWithoptionsCreate=-1` 的通用文案，也不要同时输出「截面不闭合」这类会误导的诊断。

## 问题 2（高优先级）：coordinates 求解器拒绝任何含构造几何的草图，报错文案指向实体类型，定位错误

### 现象

同一份 8 瓣星形板草图 `SK P06-02`（48 条直线 + 1 个构造参考圆 `ci01`，圆心 (52,0) R8.5）：

| 作业 | 草图内容 | 结果 |
| --- | --- | --- |
| `3822993472b2464390b62fa27dfe712f` | 48 直线 + 1 构造圆 | **失败**，`execute_sketch` |
| `748eaf662a3b4e44ba60a00e7f4815d1` | 48 直线（仅剔除构造圆） | **成功** |

失败报错：

```text
Coordinate dimensioning accepts lines, polylines, rectangles, circles and arcs only
```

`solver` 字段显示这是 `dimensioning="auto"` 依据 `entity_count` 自动选到 `coordinates` 后失败的：

```json
{"requested": "auto", "used": "coordinates", "selection_reason": "entity_count", "completed": false}
```

### 关键证据：草图里确实只有 line 和 circle

```text
Counter({'line': 48, 'circle': 1})
```

实体类型全部在报错所列的白名单内。区别仅在于那 1 个圆是 `construction: true`。因此真实原因是「coordinates 模式不接受构造几何」，而文案说的却是「实体类型不支持」，两者不一致。

### 影响

1. 报错无法定位：调用方会去检查实体类型，而实际要删的是构造几何。
2. `dimensioning="auto"` 会按实体数量静默切到 coordinates，导致同一份草图「有时能建、有时不能建」，取决于是否带参考圆。
3. `SK P06-02`/`SK P06-05` 这类带参考圆的草图在 TXT 中很常见，构造几何只是布局参考，不参与轮廓。

### 临时规避（已生效）

下发前剔除所有 `construction: true` 的实体。本轮对 `SK P06-01/02/04` 三张草图统一做了该处理。

### 建议

1. 让 coordinates 模式忽略（而非拒绝）构造几何；或
2. 至少在报错中明确指出「构造实体不被 coordinates 支持」，并在 `auto` 选择求解器时把构造实体数量计入判据。

## 问题 3（中优先级）：geometry_selector 无法区分同轴、同半径的两条圆边，round 必然匹配到多条

### 现象

Part6 主体绕 X 轴回转到 360° 后，外缘 r=220 在 x=+54 和 x=−54 各有一条完整圆边。TXT D602 只要求对 **+X 侧**那一条倒 R10，−X 侧保持尖角。

作业 `fc9874fb5c034cc682577ac7623b7089`（`execute_round`）报错：

```text
geometry_selector edge circular matched 2 edges (ids 2442, 1376);
use a smaller tolerance_mm or an anchor that belongs to exactly one edge
```

使用的选择器：

```json
{"kind": "geometry_selector", "target": "edge",
 "center_mm": [54.0, 0.0, 0.0], "radius_mm": 220.0,
 "point_mm": [54.0, 220.0, 0.0], "axis": [1.0, 0.0, 0.0],
 "tolerance_mm": 0.5}
```

### 为什么现有字段都无法消歧

- `center_mm` 对圆边是按**到轴线的垂距**比较（`geometry_selectors.py` 文档原文："center_mm is compared as the perpendicular distance to the axis line"），x=+54 与 x=−54 的垂距都是 0，`tolerance_mm` 再小也区分不了。
- `point_mm` 的语义是"narrows a split rim to the piece whose arc actually spans that angle"，只按角度切分；两条边都是 360° 整圆，角度过滤无效。
- `axis` 只约束方向，两条边方向相同。
- `endpoints_mm` 与 `center_mm/radius_mm` 互斥，且整圆的端点重合，无法用两个端点表达。

结论：**当前 selector 词汇里没有任何字段能表达"沿轴向的位置"**，同轴同半径圆边的选择在 API 层面不可达。

### 影响

回转体两侧的对称圆边是极常见的倒圆对象（只倒一侧、另一侧保持尖角）。这类需求目前只能放弃特征，或用改草图轮廓的方式绕开，等于牺牲特征树的语义。

### 临时规避（已生效）

把 R10 直接做进旋转剖面：把 `SK P06-01` 的 (54,220) 尖角替换为 R10 圆弧（弧心 (44,210)，切点 (54,210)/(44,220)），再旋转 360°。得到的环面与「在 +X 单条圆边上倒 R10」完全等价，−X 侧保持尖角。面积由 15 047.43 mm² 变为 15 025.97 mm²，最终整件体积 10 901 968 mm³，与 TXT 实测指纹 10 902 363 mm³ 相差 0.0036%，说明等价性成立。

### 建议

给圆弧边选择器增加轴向定位字段，例如：

- `center_mm` 在同时给出 `axis` 时按**绝对点**比较（而非垂距），或
- 新增 `axis_coordinate_mm`（沿 axis 方向的坐标）作为附加过滤，或
- 允许 `point_mm` 参与三维距离判断而不是仅按角度切分。

## 附：本轮已确认可用、无需修改的能力

- `datum_axis` 用两张基准面求交建轴，方向与原点正确（origin [-250,0,0]、direction [1,0,0]，轴线即全局 X 轴）。
- `depth_type` 与 `direction: "symmetric"` 对 YZ 平面草图拉伸定位准确，可绕开平面法线方向不确定的问题。
- 多轮廓草图拉伸可用：`SK P06-02` 为 8 个互不相连的闭合轮廓（8 瓣），`SK P06-03` 为 8 个圆，一次 extrude 均正确生成 8 个凸台。
- 保存/重载校验正常：`verify_model_save` 0 ms，`saved_file_reloaded_and_verified: true`。
