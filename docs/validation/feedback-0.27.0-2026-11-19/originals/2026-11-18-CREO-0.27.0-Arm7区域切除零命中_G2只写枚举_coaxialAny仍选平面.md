## 二、P1：`ExtrudeOp.region` 对真实 Arm7-S7 三条 TXT 区域签名全部零命中

**结论：0.27.0 新增的 `ExtrudeOp.region` 在 Creo 10 的真实 Arm7 数据上不可用。**

### 输入

使用 TXT 中 Arm7 `[B-CUT] sketch=Arm7-S7 depth=3 region_count=3 region_index_hint=4,2,5` 的三条真实区域签名，探针计划：

`creo_plans_v0270/arm7_region_cut_probe_ops.json`

### 实测错误

MCP 在提交/准入阶段拒绝：

```text
region signature matched none of 1 closed loops in sketch 'arm7_s7';
compare the YZ endpoints with the sketch frame, not region_index_hint
```

### 根因定位

- `sketch_regions.entity_endpoints()` 只取 line/arc/b_spline 的整条首尾端点；
- `region_selection.segments_match()` 要求段集段数完全一致；
- 当前 `arm7_s7` 只有 5 个实体，只枚举出 1 个 3 段闭环；
- TXT 三条真实签名分别为 4/4/6 段，且包含 S3/S5 交点、样条内部交点、C–D 窄缝（约 0.017591 mm）等边界；
- 结论：适配层只支持“整实体首尾端点闭环”，无法表达曲线内部交点和共享边界切分；这不是 `region_index_hint` 写错。

### 影响

Arm7 T6c 三个区域切除无法用 0.27.0 在 Creo 10 上按 TXT 原生完成。本轮 Arm7 实体只包含基础草图/拉伸和已验证的 G2 圆角探针，不包含三条真实区域切除。

### 建议

1. 区域匹配改为基于真实草图几何的交点切分和面域边界，而不是只枚举整实体端点闭环。
2. 支持共享边界与窄缝边的段切分；错误信息应区分“签名格式错误 / 坐标系错误 / 拓扑不足 / 无匹配”，不要只提示比较 YZ 端点。
3. 在发布说明中明确该能力目前只在“简单独立闭环”样例上验证，尚未覆盖真实 Arm7。

## 三、P2：`RoundOp.curvature_continuous` 仅证明字段被接受并写入枚举，未验证曲率连续性几何

**结论：能力“有”，但当前验收只能到特征树字段层，不能宣称 G2 几何已验证。**

### 证据

- 0.27.0 schema 有 `curvature_continuous: bool | None = None`。
- R30 探针第一次因 reference 写法失败：

```text
[json.exception.out_of_range.403] key 'edge' not found
```

- 改为 `references:[{"edge":{"kind":"edge","id":161}}]` 后 job `d691520433e340f2b2cbe67161d80dee` 成功。
- 特征树写入：

```xml
<PRO_E_RNDCH_CONIC_TYPE type="int">3</PRO_E_RNDCH_CONIC_TYPE>
<PRO_E_RNDCH_CONIC_VALUE type="double">0.500000</PRO_E_RNDCH_CONIC_VALUE>
```

### 缺口

目前没有公开回执给出圆角面的曲率连续性、G2 边界曲率/切向误差或原生验证字段。只能说“字段被接受且写入 `PRO_ROUND_CURV_CONTINUOUS=3`”，不能说“已实测 G2 几何连续”。

### 建议

在 job inspection 中加入 G2 圆角面的几何验证结果（例如圆角面类型、边界曲率差、相邻面切向/曲率误差），或明确说明该字段只是原生枚举写入，不提供几何保证。

## 四、P3：`coaxial:"any"` 在跨组件小圆柱配合上仍解析到平面；显式圆柱面 id 也未生效

**结论：0.27.0 修复了大圆柱拆半的一部分场景，但没有解决本 TXT 的真实跨组件配合。**

### P3.1 成功场景（证明部分可用）

2 组件探针 `d0d49700cde746e38a15080645130f65`：

- base R27.5 与 hom R25，均带 `coaxial:"any"`；
- 成功 insert，面 id 198 / 96；
- 总特征数 7，保存/重载验证成功。

### P3.2 失败场景 1：`coaxial:"any"` + radius/axis 仍选中平面

3 组件探针 `6bddd0c21cc44fc09e0d8669432e6c88`（base/hom/lateral_1）：

- lateral_1 的装配侧引用完全来自 TXT `[B-MENT] Concentric6 side=0`：
  `center=(44.215799,84.256561,44.183944)`，`axis=(-0.755022939,0,0.655698377)`，`radius=3.5`；
- 同时给了 `radius_mm=3.5`、`axis`、`coaxial:"any"`，且移除了 `points_mm` 以避免点到平面端面；
- 仍然失败：

```text
assembly_reference selector resolved to surface type 34 (plane),
but concentric/insert needs a real cylinder (PRO_SRF_CYL)
```

- 操作结果诊断：

```json
{
  "matched_geometry_id": 68,
  "candidate_count": 28,
  "target": "surface",
  "tolerance_mm": 0.001
}
```

这里匹配到的是平面 id 68，而不是 hom 的 R3.5 圆柱面 224/226。

### P3.3 失败场景 2：显式圆柱面 id 也被判成平面

把 `assembly_reference` 改为显式 `{"kind":"surface","id":224}` 后重试探针 `c88bb4fe93c14867aebb9e253c3188f3`，仍报同一错误。  
源零件 `hom_v0270` 的 inspection 明确显示：

- id 224：type 36（`PRO_SRF_CYL`），radius 3.5，axis `[1,0,0]`，origin `[19,40,0]`；
- id 226：同为 R3.5 圆柱。

因此这不是“源模型没有圆柱面”，而是解析或上下文映射问题。

### P3.4 全量配合作业同样失败

全量 23 组件、60 条约束计划 `39955536d99349159a50896948c34d32`：

- 所有 26 条 concentric 的两侧选择器都加了 `coaxial:"any"`；
- 与 2 组件探针不同，仍在第 2 个组件 `lateral_1` 失败；
- 失败消息与 P3.2 完全一致；
- 后续 20 个组件 `not_executed`；
- 新模型 cleanup 成功，job 状态 `failed`，没有生成可用配合总装。

### 影响

TXT 的 `[B-MATE]` 仍无法在真实装配上可靠建立。本轮交付的是基于 `[B-COMP]` 精确固定放置的 23 组件总装，不是带原生配合求解的总装。

### 建议

1. 在 `geometry_selector` 匹配阶段对 `coaxial:"any"` 强制只允许 `PRO_SRF_CYL`，并在诊断里输出 `matched_types` / `matched_ids`，避免静默返回平面 id。
2. 检查 assembly-space selector 映射到 sibling 组件局部坐标时是否丢失 `radius_mm`/`center_mm`/`coaxial`，或是否把 assembly 根模型的同号 id 误当成 sibling 的面 id。
3. 对显式 `{kind:'surface',id:N}` 的 assembly-side 配合引用，应按 `assembly_component` 指定的 sibling 上下文解析，并在类型检查前打印实际 owner/model/id/type。
4. 当前错误文案仍说“add radius_mm+axis”，但输入已经给了 radius+axis；应更新 runtime 文案，与 0.27.0 源码中的 BUG-132 分型文案保持一致（实测回执没有出现新文案）。

## 五、P4：`creo_execute_plan` 的大 plan_file 回执没有 compact 模式

提交 23 组件、60 条约束计划时，`creo_execute_plan` 回执约 101,506 字符，超过当前 MCP 客户端单次结果预算，被迫落盘后再读取。回执把整个 normalized operations 数组原样回显，即使调用方已经有本地 plan_file 和 SHA256。

建议：为 `creo_execute_plan` 增加 `response_detail=compact` 或只回显 `plan_file.sha256 + operation_count + job_id`，完整 operations 保留在 job detail 中按需分页读取。

## 六、P5：`model_name` 长度/字符错误文案不准确

本轮使用 33 字符的全小写名称 `coax_nopoints_lateral_probe_v0270`，返回：

```text
model_name must be 1-31 characters ... uppercase input is normalized to lowercase (BUG-069)
```

输入没有大写字符，真实原因是长度超过 31。建议分别报“too long (>31)”和“uppercase normalized”，避免把长度错误误报成大写错误。

- 未宣称 61 条 `[B-MATE]` 全部建立：当前可验证的是 23 个 TXT `[B-COMP]` 固定放置；60 条配合尝试失败/未执行。
- G2 圆角只验证到原生字段写入，未验证曲率连续性几何误差。
