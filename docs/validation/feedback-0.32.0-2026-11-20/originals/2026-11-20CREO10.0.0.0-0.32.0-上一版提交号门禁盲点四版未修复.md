### 3.4 建议修复

1. 解析 `previous_release_tag` 的 tag 对象，取 annotated tag 的 `object.sha`（或 lightweight tag 目标），确认 `object.type == "commit"`。
2. 将该 SHA 与 `docs/releases/<version>.json`、`RELEASE-<version>.md`、Release 正文中的上一版提交号逐处比较；不一致即报错。
3. 显式拒绝上一版回填提交；至少“不等于 tag 目标提交”必须失败。
4. 增加回归用例：随机 40-hex、上一版回填提交、上一版 tag 目标提交、版本/tag/commit 三者不一致，分别预期失败/失败/通过/失败。
5. 同时覆盖 `validate_release_records()` 与 `check_release_records.py --source-zip` 两条入口。

## 4. P2：Release 正文摘要说明回退

### 4.1 现象

| 项 | 0.31.1 Release body | 0.32.0 Release body |
| --- | --- | --- |
| 64-hex 数量 | 1（种子包 SHA256） | **0** |
| 四附件名出现 | 4/4 | **0/4** |
| `sidecar` 字样 | 有，且明确“源码包摘要记录在同名 sidecar 中” | **无** |

0.32.0 的 `RELEASE-0.32.0.md` 和 POSTCHECK 段都写了摘要在 sidecar，并给出完整表格；问题只出在 GitHub Release 正文没有对应指引。用户仅看 Release 页面时，无法从正文得知摘要位置。

### 4.2 门禁为什么没发现

`tools/check_release_assets.py` 只下载/校验四附件与 sidecar，没有读取或检查 Release body；本轮远端 `--tag` 仍 `exit 0`。这不代表资产损坏——本地、sidecar、API digest 都一致——只是正文自证缺口没有自动化覆盖。

### 4.3 建议修复

- Release 正文至少列出四个附件名，并写“源码包摘要记录在同名 sidecar 中”之类明确指引；若列摘要值，则必须与 sidecar 一致。
- 资产门禁增加正文检查：附件名齐全 + 摘要指引存在；若要检查摘要值，从 body 提取后与 sidecar 实值比较。
- 避免只在包内 `RELEASE-*.md` 写清楚而 Release 正文缺失，造成“分发产物齐全、Release 自证回退”。
