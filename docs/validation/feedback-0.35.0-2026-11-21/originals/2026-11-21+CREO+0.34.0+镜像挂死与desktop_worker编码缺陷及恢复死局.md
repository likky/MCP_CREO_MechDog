## §0 一句话结论

0.34.0 上 `thicken` 与单轮廓开放曲面拉伸都能精确工作（体积误差 3×10⁻¹²），但 **`mirror` 操作会让原生 worker 在 `ProFeatureWithoptionsCreate` 里永久挂死**（两次独立复现），紧接着 `unknown_outcome` 的模型进入**无法解除的 reservation**，只能弃用模型；此外 `desktop_worker._launcher` 用 UTF-8 写批处理文件、cmd.exe 却按 OEM 代码页解析，导致「只要工作目录或参数含中文就走不通」，这正是长期 `PRO_TK_BAD_CONTEXT (-4)` 的直接原因。

## §1 【已定位·可修】`desktop_worker` 的批处理编码缺陷 —— 它就是 -4 的真因

### 1.1 事实

`bridge.py:session_status()` 里 `auto` 模式在直启拿到 `-4` 时会回退到 `_desktop_probe()`，也就是 `desktop_worker.run()`。此前一直观察到「探针能连上（`worker_launch: "desktop"`）、作业一律 `-4`」，因此判断为「作业 worker 无 desktop 回退」。这个判断只对了一半：真正的第一层原因是 **`desktop_worker.run()` 对非 ASCII 路径根本启动不了**，所以它只能救「工作目录恰好是 ASCII」的场景。

`desktop_worker._launcher()` 第 179 行：

```python
script.write_text("\r\n".join(lines) + "\r\n", encoding="utf-8", newline="")
```

批处理内容里包含 `cd /d "<cwd>"`、`"<exe>" <args>`、`> "<directory>/stdout.txt"` 三类路径。cmd.exe 执行 .cmd 文件时按**控制台 OEM 代码页**（本机 zh-CN = 936/GBK）解码，UTF-8 字节被逐字节按 GBK 解释，中文全部变成乱码。

### 1.2 逐级对照实验（同一台机、同一份代码，仅改路径）

| 级别 | 命令 | 工作目录 | launcher 目录 | 结果 |
|---|---|---|---|---|
| A | `cmd.exe /c echo hi` | `C:\_creo_desk`（ASCII） | ASCII | `rc=0`，0.7 s |
| B | `cmd.exe /c echo hi` | 中文项目目录 | ASCII | `rc=0`，0.6 s |
| C | `python.exe -c "print('py-ok')"` | ASCII | ASCII | `rc=0`，0.7 s |
| D | `python.exe <ASCII 脚本>` | ASCII | ASCII | `rc=0`，0.7 s |
| E | `python.exe <中文路径脚本>` | ASCII | ASCII | **`rc=2`**，`can't open file 'E:\\...\\CREO?????_...\\_probe_child.py'` |
| F | `cmd.exe /c echo hi` | 中文项目目录 | **中文父目录** | **`None`，等满 60 s 预算超时** |

- 级别 B 说明：批处理里 `cd /d "<中文>"` 那一行会失败，但 cmd 会继续执行下一行，所以**只影响 cwd**，不致命。
- 级别 E 说明：**非 ASCII 出现在 argv 里就致命**，python 收到的是乱码文件名。
- 级别 F 说明：**非 ASCII 出现在批处理文件自身的路径里更致命**——cmd 连脚本都打不开，`exit.txt` 永远不生成，调用方只能等到超时后返回 `None`。

### 1.3 为什么这表现为 -4 而不是明确的报错

`desktop_worker.run()` 的失败是**静默的**：`_launcher()` 返回 `None` / 等不到 `exit.txt` / `_explorer_shell()` 抛 `DesktopUnavailable`，三条路径统一 `return None`。`bridge._desktop_probe()` 见到 `None` 就只给 `value["desktop_retry"] = "unavailable"`，`toolkit_code` 仍是直启的 `-4`。于是**调用方看到的是「-4，且桌面回退不可用」，而不是「桌面回退因中文路径无法启动」**，这个误导让我在环境层面折腾了多轮。

### 1.4 修法（按优先级）

1. `_launcher()` 改为按 `locale.getpreferredencoding(False)` 或显式 `"mbcs"` 写批处理；或者在脚本开头写 `chcp 65001 >nul` 并用 UTF-8。Windows 上更稳的做法是直接 `encoding="mbcs"`。
2. 更稳的结构：不要让 cmd 承担路径拼接。用 `subprocess.Popen(..., creationflags=..., startupinfo=...)` 由 explorer 只启动一个**极短的 ASCII 中转 exe/py**，再由它自己用 Python 起真实命令（Python 全程 Unicode，不经 cmd 解码）。
3. `_launcher()` 的每个 `return None` 都要带原因，并让 `_desktop_probe()` 把原因放进 `desktop_retry`，不要退化成 `"unavailable"`。
4. `run()` 的 `finally: shutil.rmtree(directory)` 失败不应影响返回值（见 §2）。

### 1.5 绕法（我方已采用，可供其他用户参考）

把驱动脚本、steps、out 全部暂存到纯 ASCII 目录（本项目用 `C:\_creo_desk\stage_<HHMMSS>_<pid>\`），argv 里不出现任何非 ASCII。改完后：

```
ready in 6s
{"message": "Toolkit connection verified; modeling is available"}
```

**作业侧立刻可用**——同一台机、同一个 Creo、同一份 0.34.0，什么都没重装。

## §2 【环境相关】沙箱的文件删除拦截会让 `desktop_worker.run()` 全线失效

在启用文件系统保护的宿主里（本次为 WorkBuddy 沙箱），`desktop_worker.run()` 的 `finally: shutil.rmtree(directory, ignore_errors=True)` 被 safe-delete 策略拦截，日志形如：

```
[safe-delete][SAFE_DELETE_FAIL_CLOSED] {"target": "C:\\_creo_desk\\runs\\...", "reason": "trash-failed",
 "detail": "... Error during a `trash` operation: Unknown { \"Some operations were aborted\" }"}
DESKTOP LAUNCH UNAVAILABLE
```

表现是 `run()` 稳定返回 `None`，`DESKTOP LAUNCH UNAVAILABLE`，**与 Creo 状态无关**。同一命令在关闭沙箱后 100% 成功。

建议：`run()` 把清理与启动解耦——清理失败只记 warning，不参与返回值判定；或者把临时目录建在 `tempfile.gettempdir()` 下并允许 `ignore_errors` 静默失败。

## §3 【阻断级】P16：多轮廓**开放**截面的曲面拉伸被 Toolkit 拒绝

### 3.1 现象

`sketch` 里两条互不相连的平行线（TXT Sketch6：`(62.3, 6.9)`→`(46.3, 6.9)` 与 `(62.3, -6.9)`→`(46.3, -6.9)`，米→mm 后 y=±690），`extrude mode="surface"`：

```
Extrude feature creation failed (ProFeatureWithoptionsCreate=-1). Toolkit rejected the referenced
sketch section; ... Detected native section: 0 closed contour(s), 2 contour(s), 2 entity(ies),
4 open end(s). The section carries open ends, so it is not a closed profile.
Max open endpoint gap 1380 mm ... Sketch: 'sketch6'.
```

### 3.2 对照

- 同一 `mode="surface"`、**单条**开放直线（TXT Sketch4）→ 成功，quilt 面积 72,000 mm²。
- 所以不是「开放截面不被支持」，而是「**一个 section 里放多个开放 contour** 不被接受」。

### 3.3 影响与绕法

TXT 的 `Surface-Extrude2` 是一条特征带两块对称板，只能拆成两个曲面拉伸。我实测拆开后两块 quilt 各 288,000 mm²，与 1600×180 完全一致，几何等价，代价是特征树多一层、丢失「同一特征的双侧对称」语义。

建议：在 surface extrude 路径放宽为「每个开口 contour 各生成一个面」，或在返回里明确指出「多 contour 开放截面需拆分为多个 section」而不是统一报 `0 closed contour(s)`。

## §4 【阻断级·最高优先】P17：`mirror` 操作把原生 worker 挂死在 `ProFeatureWithoptionsCreate`

### 4.1 两次独立复现

**第 1 次**（job `1c6bd630faca4586bbee3e5d2e1d17c1`，模型 frigate_v2）

plan = `sketch` + `extrude(surface)` + `mirror` + `thicken`

`native.log` 尾部（44029 字节，写于 15:55 后完全停止增长）：

```
ProMdlToModelitem(board, &mi)=0
ProSelectionAlloc(nullptr, &mi, &s)=0
ProArrayAlloc(1, sizeof(ProFeatureCreateOptions), 1, (ProArray *)&opts)=0
```

紧接着 `ProFeatureWithoptionsCreate` 那次调用**永不返回**。看门狗 601 s 无日志增长后终止 worker，作业终态 `unknown_outcome`。

**第 2 次**（job `ca661ffd86334f2da2ccd4937185e624`，模型 frigate_v3，rev3 已含两块板+加厚）

plan = 只有一条 op：`mirror`（`plane: {"kind":"datum_plane","id":4}`，`references: [{"kind":"feature","label":"a_surf1"}]`，`keep_original: true`）

`native.log` 尾部**逐字节同样**停在 `ProArrayAlloc(1, sizeof(ProFeatureCreateOptions), 1, (ProArray *)&opts)=0`。

### 4.2 归因排除

- 不是 `thicken`：单独的 `thicken`（job `d364aed0…`）成功，体积精确 +144,000。
- 不是多轮廓：`mirror` 只在单轮廓 quilt 上就挂。
- 不是参考语法报错：`quilt_feature` / `datum_plane label` / `datum_feature` / `datum_plane id=3(特征id)` 这几种错误写法都在**校验阶段**就返回了明确错误，不会进到 native。唯一通过校验、进入 native 的写法（`{"kind":"datum_plane","id":<几何id>}` + `{"kind":"feature","label":…}`）才挂。
- 不是磁盘/权限：同批次前后 `sketch`/`extrude`/`thicken` 都正常写模型。

### 4.3 后果链（这是最需要修的地方）

```
mirror → ProFeatureWithoptionsCreate 挂死
      → 601 s 无日志增长 → 看门狗终止 worker
      → 作业 unknown_outcome
      → 模型 status=unknown_outcome，pending_job 保留
      → Creo 消息循环被阻塞 → 后续所有呼叫 -38 (PRO_TK_E_BUSY)
      → 必须结束父进程重启整个 Creo
      → 重启后会话指纹变化 → reconcile 的 restore_baseline 变为不可用
      → 模型永久报废（§5）
```

一次 `mirror` 的代价是：一个模型 + 一次 Creo 重启 + 十几分钟。

### 4.4 建议

1. 先复现：单独一条 `mirror`（quilt 上的 `kind: feature` 引用 + `datum_plane` 几何 id），在一个只有「放样基体 + 一个曲面拉伸」的零件上执行。
2. 若确认是原生调用卡住，给 `ProFeatureWithoptionsCreate` 套一层超时/取消，至少让它返回错误码而不是永久阻塞。
3. 在 `keep_original=true` 的 surface 镜像路径上，考虑改走「复制 quilt + `geometry_transform` 绕平面翻转」这类已验证路径，避开 feature mirror。
4. 挂死被看门狗终止后，**必须**能自动判定「worker 已死」并释放 reservation；见 §5。

## §5 【阻断级】P18：`unknown_outcome` 之后的恢复是死局

### 5.1 事实

模型 `frigate_v2` 在 §4 挂死后，按提示逐级走恢复：

1. `creo_reconcile_model(mode="inspect")` → `status=unknown_outcome`，`actions.restore_baseline.available = true`，取到 `evidence_token`。
2. `creo_reconcile_model(mode="apply", action="restore_baseline", expected_revision=1, expected_pending_job_id="1c6bd630…", evidence_token=…, idempotency_key=…)` → `status="queued"`，`message="Recovery accepted; poll this job_id; original plan will not be replayed"`，`job_id=dd40a024015a485babe88f82a88cb8eb`。
3. 轮询三次（每次 `wait_seconds=120`，跨度约 6 分钟）→ 一直是 `status="queued"`, `stage="intent_persisted"`，**永不前进**。
4. 再次 inspect → 所有 action 变为不可用：

```
"Previous runner/worker is active or cannot be proven stopped"
```

5. 此时 `jobs/dd40a024…` 的 owner 记录里的 pid（`native_owner.json`）已经**不存在**；`Get-Process -Id` 确认进程已退出。而 `creo_startup_status` 报告 `state=ready, connected=true, blocking_job_id=null`。

### 5.2 判定逻辑的问题

「无法证明已停止」用的是**会话指纹 + pid**。挂死期间看门狗终止了 worker、Creo 随后被重启（新 xtop），会话指纹从 `2385047794368141048` 变成新的值。旧指纹的会话已经不存在，这本身就是「已停止」的最强证据，但判定把它当成了「无法证明」。

结果：**唯一可用的 restore_baseline 也变成不可用，模型永久报废**，而它在磁盘上的 `frigate_v2.prt.2` 是健康的（sha256 `e20d2fd1…`，与 baseline 一致，体积 4,173,714,361.414）。

### 5.3 建议

1. 判定应覆盖「owner pid 不存在」+「会话指纹已换代」两种情况，二者任一成立即可视为已停止。
2. 恢复作业 `intent_persisted` 长时间不前进时，应给出「等待原因」字段，而不是只回 `queued`。
3. 提供 `abandon_model` / `discard_model` 的出口：既然磁盘基线健康，允许用户显式丢弃这个 model_id 并释放 model 名，避免每个失败模型都永久占着名字和一个不可用的 id。
4. 反向建议：`expected_pending_job_id` 为 null 时（无 pending）允许直接 `ack_no_mutation` 把模型拉回 ready。本例中磁盘 sha 与 baseline 完全一致，实际就是零变更。

## §6 参考语法陷阱（都花了实际时间，建议写进工具文档）

| 用途 | 错误写法 | 报错 | 正确写法 |
|---|---|---|---|
| mirror 的镜像面 | `{"kind":"datum_plane","label":"TOP"}` | `Kind 'datum_plane' plane references resolve by id/axis/normal and do not honour a label` | `{"kind":"datum_plane","id":4}`（**几何 id**，来自 `inspect_model(section="datum_planes")`） |
| mirror 的镜像面 | `{"kind":"datum_feature","label":"TOP"}` | `Unknown feature label: TOP; available labels: deck_outline, hull, lower_outline, …` | 同上；默认基准面不在 plan 的 label 索引里 |
| mirror 的镜像面 | `{"kind":"datum_plane","id":3}`（特征 id） | `Datum plane geometry id not found: 3` | 必须用几何 id（TOP 是特征 3、几何 4） |
| mirror 的镜像面 | `{"kind":"plane","normal":[0,1,0],"offset":0}` | `Plane reference must identify exactly one surface; 0 candidate surface(s) match` | 这个形式只匹配**已存在的平面面**，不凭空建面 |
| mirror 的被镜像对象 | `{"kind":"quilt_feature","label":"x"}` | `Toolkit mirror accepts geometry, part, or feature-label references` | `{"kind":"feature","label":"x"}` |
| thicken 的参考 | `{"kind":"feature","label":"x"}` | — | `{"kind":"quilt_feature","label":"x"}` 或 `{"kind":"quilt","id":N}` |

补充：`inspect_model(detail="full")` 不带 `section` 时，`data.surfaces`/`data.bodies`/`data.datum_planes` 会是**空数组且 `complete=false`**，容易被误读成「模型里没有基准面」。必须显式 `section="datum_planes"` 才拿得到几何 id。

## §7 已验证可用的能力（供作者做回归对照）

| 操作 | 实测结论 | 证据 |
|---|---|---|
| `creo_new_loft_part`（2 截面，straight） | 稳定，~20 s | 体积 4,173,714,361.414，与另一零件完全一致 |
| `extrude mode="surface"`，单条开放线 | 稳定 | quilt 面积 72,000 / 288,000 mm²，bbox 精确 |

`thicken` 的 `side` 语义实测：quilt 法线恒为 +Y 时，`side="negative"` → 沿 −Y 偏移（对 y=+690 的板是船内）；`side="positive"` → 沿 +Y（对 y=−690 的板是船内）。建议文档里点明 `side` 是**相对 quilt 法线**，而非相对船体或坐标系。
