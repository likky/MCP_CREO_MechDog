## 三、核心问题：BUG-137 修复引入打包门禁顺序依赖，全量单测结果取决于上次运行遗留的报告

### 1. 现象：同一份源码、同一台机器，两次全量单测得到两种不同失败

```text
# 第 1 次（期间并发跑过 dev_check，导致一个子进程 ModuleNotFoundError）
build/unit_test_report.json: 4297 项, 0 failures, 1 errors, 4 skipped, success=false
ERROR: test_window_refusal_never_publishes_a_removed_reference
       (unit.test_adoption.AdoptionMcpContract) — MCP Connection closed
       子 server 报 ModuleNotFoundError: No module named 'creo_mechdog'

# 第 2 次（严格无并发、干净重跑）
build/unit_test_report.json: 4297 项, 3 failures, 0 errors, 4 skipped, success=false
FAIL: test_valid_seed_archive_packages_a_new_empty_stage_directory
FAIL: test_valid_seed_archive_packages_the_source_with_the_default_output
FAIL: test_valid_seed_archive_packages_the_source_with_the_explicit_output
  (unit.test_release_integrity.SeedPackagingGateTests)
  断言失败信息：
  [release-gate] 0.35.2 unit test report: success=False, tests_run=4297,
                 failures=0, errors=1, skipped=4
  Release record gate rejected this package:
    - source tree: release record claims 全量 unittest 通过 but
      build/unit_test_report.json reports success=false ...; do not write
      全量通过 until tools/test_unit.py reports success=true
```

注意第 2 次的失败信息里写的是 `errors=1`——那是**第 1 次**运行留下的数字，不是第 2 次自己的（第 2 次是 3 failures / 0 errors）。这就是问题的铁证：打包用例读到的是磁盘上**上一次**的报告。

### 2. 根因：测试产物被当作测试输入，形成跨轮次污染

调用链：

1. `tools/test_unit.py` 只在**全部测试跑完后**才一次性写 `build/unit_test_report.json`（`tools/test_unit.py:27`）。测试运行期间，磁盘上这份报告一直是"上一次运行遗留"的版本。
2. `tests/unit/test_release_integrity.py` 的 `SeedPackagingGateTests` 三个**正向**打包用例（约 303/320/336 行）调用 `tools/package.py` 打包源码。
3. `tools/package.py:181-190` 调用发布记录门禁；`src/creo_mechdog/release_integrity.py` 的 `_unit_test_claim_problems()`（1496 行）因 `RELEASE-0.35.2.md` 写了"全量 unittest 通过"，就去读取工作区共享的 `build/unit_test_report.json`（常量 `_UNIT_TEST_REPORT = "build/unit_test_report.json"`，1437 行），要求 `success=true`，否则拒绝打包并让 `package.py` 返回非 0。
4. 于是这三个用例的成败 = f(上次测试留下的报告)，与本次被测代码无关。

引入点：`_unit_test_claim_problems` 与"全量通过须 success=true 报告"的门禁是 **0.34.0 提交 `bbd81cd`**（正是交付我方 BUG-137 修复的那批）新增的；而 `SeedPackagingGateTests` 正向打包用例更早（`ecda0f2`）就存在。两者叠加即产生该顺序依赖。这是修 BUG-137 时未料到的回归：**为了让发布口径诚实（正确目标），却让单元测试依赖了共享的可变产物**。

复现验证（本机实测）：

```text
# 把 build/unit_test_report.json 的 success 从 false 翻成 true（其余不动）
$ python -m unittest tests.unit.test_release_integrity.SeedPackagingGateTests -v
Ran 7 tests in 74.7s → OK    # 三个失败用例立刻全过
```

报告翻回 false 后三者必失败——确定性可复现，与产品功能无关。

### 3. 影响

- **全量单测无法自证全绿**：任何一次失败（哪怕来自并发干扰、环境问题或偶发竞态）都会污染下一轮，使 `dev_check.py` / CI 的 `unit_tests=failed`，发布证据不可复现。
- **失败对象漂移、误导定位**：本轮先报 adoption 的 MCP `Connection closed`，再报 release_integrity 的打包门禁，实际两者都不是被测代码缺陷，而是报告状态与并发副作用。
- **干净工作树掩盖问题**：作者发布环境每次都是 success=true 的干净报告，正例用例恒过，因此官方"4297 项全绿"与用户真实升级工作区长期不一致——这与我方反馈 BUG-137 时的"发布口径 vs 真实复验"是同一类问题的延续。

### 4. 修复建议

1. **隔离测试输入**：`SeedPackagingGateTests` 的正向打包用例应使用临时数据根/临时工作树（复制一份 `success=true` 的 `unit_test_report.json` 与发布记录进去），不要读取真实工作区的 `build/unit_test_report.json`。项目已有 `--data-root` / `main_worktree` 这类夹具模式可复用。
2. **给门禁开测试旁路**：`release_integrity._unit_test_claim_problems` 支持通过参数/环境变量指定报告路径（如 `MECHDOG_UNIT_TEST_REPORT`），测试指向自己的夹具报告；生产路径仍默认工作区报告。
3. **报告写入原子化且测试期间不残留误判**：`test_unit.py` 开始时先把报告置为"running/unknown"（而非沿用上次结果），或让打包门禁在报告 `success` 为陈旧时间戳时明确报"报告未更新"而非直接判拒。
4. **补一条回归用例**：在"工作区报告故意为 success=false"的前提下，正向打包用例仍应通过（证明已隔离），防止再次回归。
5. 附带（P3）：把 README 第 17 行"**109 个公开工具**"同步为 110。该数字在 0.34.0 引入第 110 个工具（`creo_redefine_solidify_body`）时漏改，README 第 5、9 行已是 110，跨 0.34.0～0.35.2 三个版本不一致。既然 BUG-138 已把断言与 `UPDATE_CHECK.md` 解耦为"以 `creo_capabilities` 为准"，建议 README 特性段落也去掉硬编码数字或纳入同一门禁，避免再次漂移。

## 四、次要观察（不作为缺陷主张）

- **dev_check 的 style 回归检查作用域覆盖仓库根目录所有 `.md`**：本机在仓库根目录放 13 份历史反馈文档（未跟踪），`dev_check.py --skip-unit` 会把其中 3 份判为 "new or changed file must pass its formatter" 并提前中断，连离线门禁都跑不到。这些文档作者已归档到 `docs/validation/`，本机只是留存副本。建议 style 检查仅针对 git-tracked 且本次变更的源码文件，或排除 `*.md`，避免用户在仓库根目录写笔记就让官方门禁失败。
- **`clang-format` 只在 `requirements-dev.txt`**：仅装 `requirements.lock.txt` 时 `dev_check.py` 会报 `No module named 'clang_format'`。AGENTS.md 已说明需另装 dev 依赖，属预期，非缺陷。
- **冒烟期启动锁**：本轮冒烟未出现 `Startup coordination lock access failed`；该警告在旧版本已有，属本机已有 Creo 占锁的环境行为，代码分类为 `lock_error`，不计为产品问题。
- **未验证范围**：Creo 9 实机建模 / Toolkit 连接（按会话纪律）、Creo 10/12 本轮未复测、WorkBuddy 黑盒 MCP 验收。若要在 WorkBuddy 使用新的 110 个工具，需重启 MCP 连接器。
